# Flutter 多设备资料库与播放重构（1.4.0）

本次修改覆盖 Flutter 客户端、Core 资料库身份、音频来源和播放会话。开发环境为 Flutter 3.44.1 / Dart 3.12.1，未升级共享 Flutter SDK。原始音乐文件不改写、不搬移、不删除；客户端使用新的缓存和离线索引，不迁就旧缓存格式。

## 数据职责与协议

- Core 维护统一的曲目、专辑、艺术家和歌单；客户端上传自己设备的目录清单。
- 资料库身份由 `server_id + catalog_epoch` 共同确定。数字曲目 ID 不可跨身份复用。
- 客户端快照通过 `device_id` 获取本设备的文件绑定；绑定变更不删除设备上的物理音乐文件。
- 客户端只使用 `/client-sync/changes`、`/client-sync/snapshot` 和 `/client-sync/details`。已删除旧端点拼接快照、旧版详情接口 404 降级和重复快照包装函数。
- changes、snapshot 和 details 均需返回资料库身份。新版 Flutter 应与本次修改后的 Core 一起部署；不再静默兼容缺失身份字段的旧 Core。

## 修复的边界

| 场景 | 调整 |
| --- | --- |
| 查询变更后有并发写入 | Core 的游标变化即要求快照；客户端仅在游标未变且变更为空时跳过下载，不从空变更响应推进游标。 |
| 变更列表超过 500 条，或快照包含后续变更 | 不能据截断列表推断全部详情范围，改为刷新全部详情类型。完整覆盖的收藏变更仍避免无必要的详情下载。 |
| 首次刷新重复拉取快照已有内容 | 直接使用快照中的设置、历史和统计，将快照后的补充请求从 9 个降为 4 个；无新快照时统一读取 `/settings`。 |
| 手动刷新与后台同步并发 | 资料库刷新串行执行；请求固定 Core 地址，旧连接响应不能写入新连接的当前状态。 |
| 快照下载成功、持久化失败 | 先完成 SQLite 快照写入，再应用内存快照及其游标。 |
| Core 重建、切换或返回不完整快照 | 校验 server、epoch、游标及必要列表，拒绝错误响应；统一在身份处理入口重置逻辑 ID。 |
| 后台详情下载因离线、扫描或连接切换暂停 | 保留最后已保存页及待刷新状态，只有末页成功保存才完成；非递增分页响应报错。 |
| 收藏请求失败或和重试并发 | 在线收藏写入与离线重试共享串行队列；后台同步定期重试，只移除本批次被确认的 ID。 |
| 还有未确认收藏时收到服务端快照 | 将待上传的收藏意图投影到界面，保留服务端其他字段，不自行制造满分评分。 |
| 移除目录时仍在扫描上传 | 移除和扫描使用同一队列；前一任务失败不阻塞后续任务。扫描固定连接及资料库身份。 |
| 自动重连发现其他 Core | 自动发现只接受原 server_id；显式发现操作可以选择新 Core。 |
| 文件绑定、曲目或搜索结果被删除 | 清理不再存在的本地逻辑绑定、详情和搜索缓存；正在扫描的目录暂缓绑定清理。 |
| 保存离线状态时进程退出 | 临时文件落盘后直接 rename 覆盖，去除先删除原文件的空窗。 |

## 统一曲目与设备副本

逻辑歌曲、发行位置、音频编码和物理文件分开。不同设备的 FLAC/M4A 副本可以属于同一首歌；Core 取流按专辑发行身份查找副本，歌曲详情按专辑卡片展示同一录音的关联发行，不能把手机的占位 URI 当成 Core 文件路径。

自动识别使用标题、艺术家集合、专辑、版本、碟号、曲序和时长。只有唯一已知年份且整组时长差不超过 2 秒时，才允许缺少年份的转码副本加入。现场版、不同曲序、冲突年份、缺少必要标签的文件不做猜测合并。保留各来源的独立身份，使后续标签纠正可以撤销自动关联；人工确认关系不被自动匹配覆盖。

`visible_catalog_tracks` 统一歌曲列表、首页计数、搜索、详情同步和设备绑定使用的有效 ID。智能歌单通过一次集合查询应用这一过滤，不在每首歌曲上重算视图；真实数据副本的完整歌曲、艺术家、专辑和歌单查询各在 0.5 秒以内完成。一个来源移除后，其他有效副本不会因为旧来源 ID 较小而从列表消失。专辑详情分页只枚举存在有效曲目的规范专辑，跳过旧别名与失效专辑。

## 播放会话与解码器

- Flutter 在线操作统一走播放会话协议；删除旧 HTTP 降级、提前本地启动音频、重复队列算法和数字索引兼容逻辑。
- 每个输出独立管理队列与解码器。队列中的每次出现有独立 UUID，同一首歌出现多次也不会混淆。
- 每次换源创建新解码器，并隔离上一首的延迟回调。打开音源后，只有实际解码位置推进才上报 playing；启动失败或长时间不推进会明确停止并显示错误。
- 播放进度来自解码器；缓存中的 playing 状态不会在重启后冒充真实播放。暂停、缓冲、失败、自然结束分别处理。
- 自然结束提交绑定当前输出和命令序号的 Complete 操作。Core 串行检查后只推进一次；普通 stopped、迟到的旧曲结束和重复请求都不能误触发下一首。
- Core 自身输出也使用同一套队列推进规则；顺序、单曲循环、列表循环和随机播放语义一致。
- 待重试命令保存原始命令 ID、会话、epoch 和 revision，不把过期操作重新包装成新操作。Core 重启递增会话 epoch，阻止旧进程的未确认操作污染新会话。
- WebSocket 只推送实时播放命令，且只发给对应设备。重连读取当前会话，彻底取消历史播放命令重放，避免几小时前的命令造成重连循环。
- 心跳、进度上报和输出刷新独立于大批资料库下载。流媒体设备即使没有离线副本，也会在 Core 地址变化后重新发现同一个 server_id；冷启动连接失败也会自动重试。已知主机优先探测新端口，mDNS 发现有 10 秒总时限。

## 1.3.1：设备在线与专辑版本边界

2026-10-04 根据真实设备和 Cruel Summer 的反馈进一步修改：

- 在线状态使用 renderer 的 35 秒心跳租约。扫描时间与文件 `ready` 仅表示库存，不能证明设备在线。注册、播放状态和音量状态上报续租；Core 重启清空租约。无音乐文件的设备也会进入设备列表。
- 资料库的设备、来源、可用数量、文件状态筛选和歌曲副本状态使用同一租约。Flutter 删除基于五分钟前扫描和离线输出仍判在线的逻辑，页面每五秒更新状态；失联副本不再显示可用。
- `release_identity_id` 表示同一专辑、曲序、版本的跨格式副本。录音关联不再折叠不同专辑的歌曲入口，也不允许另一张专辑的文件充当当前专辑的播放源。同步绑定、手动文件解析和智能歌单的来源查询均使用发行身份。搜索、艺术家页与专辑页删除重复的录音折叠查询，统一读取可见发行列表；实测两个发行版本均可搜索到，Lover 与 The Eras Tour 的详情分别返回 19、46 首曲目。
- 关联和拆分覆盖一个专辑版本的全部设备、编码副本。历史上同专辑各副本保存了不同录音关联时，采用最近一次明确关联决定；后续扫描保留这个结果。不同专辑仍有独立歌词与文件。
- 详情与管理页面复用专辑卡片；格式、设备、音质和在线状态是卡片内标签。删除旧的作品/录音层级、格式大卡片、空媒体占位卡和本地副本随意附到首选格式的兜底。
- 新目录身份使客户端重建派生缓存；不保留旧协议的缺字段兼容。原音乐文件未改写、移动或删除。

## 1.4.0：歌曲展示属性与流派整理

- 同名展示分组使用规范化歌名与主艺术家集合；缺少艺术家的条目不自动合并。该分组不代表相同录音，专辑收录身份、文件来源和收藏状态保持独立。
- Core 配置 `song_display.merge_same_name` 提供全局默认；Flutter 每个歌曲列表可临时覆盖，单曲属性为 `inherit` / `merged` / `independent`。属性持久化在 `track_display_preferences`，通过发行收录身份共享给同版的编码副本和后来导入的副本。
- 搜索支持中文属性名与流派；各列表提供展示属性筛选和排序；智能歌单增加 `display_mode` 条件。
- 合并行可打开专辑版本选择。播放全部使用显示组的可用代表，单行播放也使用当前显示列表生成队列。已有队列仅折叠展示，展开后操作始终使用原始队列项 ID；不改变顺序、重复项或历史事件。
- 歌曲、歌单、专辑、艺术家、搜索、首页历史、历史统计、播放队列均接入展示控制。全局设置通过设置事件和同步快照传播到其他设备。
- 流派导入、客户端清单和手工编辑统一使用保存的分隔符；精确复合词规则包括国语、粤语、英语、日语、韩语、华语、闽南语加“流行”，支持对应繁体写法。不按任意子串切分，不会破坏 `R&B/Soul`（除非用户显式设置斜杠为分隔符）。
- “保存规则并拆分已有流派”在一个事务内重建流派关系和搜索索引。保留原文件元数据证据，重复执行无新增变化。所有操作均不写入原始音乐文件。
- 共用歌曲查询构造器，移除重复 SELECT。可用来源查询固定从当前发行版的少量曲目 ID 出发，避免 SQLite 从全库的文件扫描状态索引开始关联；6061 首真实资料的全曲目查询约 250–650 毫秒（本机并发构建时有波动）。
- 验证：61 项 Rust 测试、81 项 Flutter 测试；涵盖跨专辑身份保持、后来副本继承、重扫保持、属性搜索与智能规则、复合流派幂等、手机/桌面播放集合及队列重复项定位。
