# Core 隐藏智能歌单需求

本文供 Core 开发与客户端后续接入使用。目标是将首页的“今日随听”“新近入库”改为由 Core 统一维护的系统隐藏智能歌单，而不是由各客户端临时选曲。当前阶段只整理需求，不实现 Core 或继续修改鸿蒙客户端。

用户已明确：全局设置可以提供管理开关；用户能够修改隐藏智能歌单的规则，但不能删除这些歌单。以下接口名称、默认数量和性能指标是建议方案，可在 Core 开发时调整并记录最终协议，行为与保护边界应保持一致。

## 已有能力与缺口

依据 2026 年 10 月 4 日工作区代码核对，不代表运行中 Core 已具有下述新增能力。

- 已有普通手动歌单和智能歌单，支持规则的全部匹配或任一匹配，以及歌手、专辑、流派、收藏、评分、资料库来源等条件。
- `PlaylistSummary` 尚无系统身份、隐藏属性或操作能力声明；普通歌单删除函数直接删除对应记录，没有系统歌单保护。
- 智能歌单查询固定按歌曲标题排序，尚无本需求需要的随机批次和入库时间排序；详情接口目前取前 1,000 首，需要避免把截断结果当成完整歌单。
- 普通歌单列表、搜索、客户端同步快照复用歌单查询，必须一并处理隐藏逻辑，不能只在新客户端界面过滤。
- 规则解析对不支持的字段存在忽略行为。新增规则写入必须严格校验，不能静默保存成另一种选曲结果。

相关实现入口：`crates/protocol/src/lib.rs`、`crates/core-db/src/playlists.rs`、`crates/core-db/src/helpers.rs`、`crates/core-db/src/smart_playlist_sources.rs`、`crates/core-api/src/playlist_routes.rs`、`crates/core-api/src/settings_routes.rs`、`crates/core-api/src/sync_routes.rs`。

## 系统身份与生命周期

复用已有智能歌单引擎，增加“系统维护、普通入口隐藏、禁止删除”的身份。隐藏只影响产品展示，不是保密或访问授权机制。

- 每个资料库内用稳定的系统键标识用途，例如 `daily_mix`、`recently_added`。客户端按系统键查找，不硬编码数据库数字 ID，也不靠中文名称判断身份。
- 系统键在同一资料库中唯一。首次升级自动创建；重复迁移、重启和并发初始化不得创建重复歌单。
- 类型固定为智能歌单，系统键、系统归属、隐藏标记和删除保护不可由普通更新接口修改，也不能转换为普通手动歌单。
- 用户自建同名歌单仍是普通歌单，不自动接管、合并或删除。
- 后续升级保留用户已经修改的规则；默认规则带版本，规则迁移须保留备份或有明确恢复办法。不得每次启动用默认规则覆盖用户设置。
- 所有结果、缓存和写入沿用 `server_id` 与 `catalog_epoch` 身份隔离。切换 Core 或重建资料库后不得复用旧数字 ID、规则编辑请求或结果快照。

建议返回字段：`system_key`、`is_system`、`hidden`、`rules_revision`，以及 `can_edit_rules`、`can_delete`、`can_edit_tracks` 等操作能力。系统歌单的后两项始终为 false；能力字段只是给客户端使用，服务端仍须独立校验。

## 首批歌单

### 今日随听

从符合规则的可见曲库中随机选择一批歌曲，建议默认 30 首，候选不足时返回实际数量。不能固定取标题排序后的前若干首，也不能只随机第一首而后续列表固定。

- 保存随机种子、批次标识和生成时间。相同批次在翻页、返回页面、不同客户端读取时顺序一致；普通读取不重新抽样。
- 默认每天更新，并提供显式“换一批”。日期由 Core 统一判定并返回下次刷新时间，不受各客户端时区差异影响；Core 未配置时区时须使用并说明统一默认时区。
- “换一批”生成新的随机结果及顺序；候选足够时应尽量降低与上一批的重合，不承诺小曲库也能完全不重复。仅一首或没有符合条件的歌曲时返回真实结果。
- 支持在规则中限制歌手、专辑、流派、收藏、评分、资料库来源等；建议增加每位歌手或每张专辑的数量上限，让用户可调节选曲多样性。
- 随机刷新与编辑规则是两件事。管理开关关闭时，用户仍能在首页“换一批”；这不会修改持久规则。
- 此阶段是规则选曲和随机抽样，不宣称拥有个性化推荐模型。

### 新近入库

动态展示最近加入的歌曲，建议默认最近 100 首，支持用户修改数量上限和可选的最近若干天范围。

- 按入库时间倒序排列，相同时间使用稳定的第二排序键，不能按名称或扫描返回顺序排列。
- 明确“入库时间”采用当前目录中歌曲的入库字段，不能把一般元数据编辑、重新扫描和客户端缓存时间当成新入库时间。重复副本增加、合并和拆分时的时间语义须有测试。
- 目录新增、移除、合并或影响筛选规则的资料变更后更新结果；翻页期间用结果版本保持一致。
- 首页只展示少量预览，进入详情能读取完整结果。预览数量、规则限定的结果总数、候选匹配总数应区分，不能把首页 6 首预览当成整张歌单。

两类歌单都遵守 Core 已有的可见歌曲与版本展示规则。不按同名歌手或同名歌曲擅自去重；不把同一展示身份的文件副本当作多首推荐。建议规则支持“仅当前可用”，但 Core 可用状态不等于任意目标设备必定可播放，实际播放仍使用现有音源解析与错误处理。

## 全局设置与管理范围

建议在 Core 级全局设置增加“管理隐藏智能歌单”，默认关闭，并持久化同步给各客户端。此处“全局”指连接同一个 Core 的客户端共用，不是单台手机偏好；多用户个人偏好不在本阶段范围内。

建议开关说明：开启后可在设置中调整系统隐藏歌单的筛选和生成规则，不支持删除歌单。

| 行为 | 开关关闭 | 开关开启 |
| --- | --- | --- |
| 首页读取、查看、播放隐藏歌单 | 允许 | 允许 |
| 今日随听换一批 | 允许 | 允许 |
| 普通歌单列表、搜索、添加歌曲目标中展示 | 不展示 | 仍不展示 |
| 设置中的专用管理入口 | 隐藏 | 展示 |
| 修改规则、预览未保存规则、恢复默认规则 | 禁止 | 允许 |
| 删除、转普通歌单、解除隐藏、手工增删成员 | 禁止 | 禁止 |

开关不是歌单功能总开关：关闭不能清空歌单、停止首页供给、重置用户规则或中断播放。

管理页允许修改筛选条件、匹配方式、结果数量，以及对应歌单支持的生成参数。首版不开放修改系统键、歌单用途和系统名称，避免“新近入库”被改成另一类集合。恢复默认规则需要确认，但不删除重建歌单，不改变其稳定身份。

服务端应拒绝管理开关关闭时的规则写入和恢复默认请求，避免另一个客户端关闭开关后，旧编辑页仍能提交。该开关不是新的安全认证机制，相关接口继续沿用项目现有的配置修改权限。

## 删除保护必须由 Core 执行

不能仅隐藏客户端“删除”按钮。已知 ID 的旧客户端、直接 HTTP 请求以及未来批量删除路径都必须无法删除系统隐藏歌单。

- 在共享业务或数据库访问层检查系统身份，再执行删除，确保所有调用方生效。
- 普通更新接口不可通过清除隐藏标记或改类型绕过保护；未知或不可写字段应明确拒绝，不能返回虚假的成功结果。
- 禁止手工添加、移除、清空和重排智能歌单成员；应修改规则或生成新批次。清空当前播放队列则是独立且允许的播放操作，不得混同。
- 给出稳定、可识别的错误码，例如 `system_playlist_protected`、`system_playlist_management_disabled`。禁止删除时不得修改数据或发布成功删除事件。
- 整库重建、备份恢复属于已有资料库维护流程，不是管理页面的删除能力；需记录系统歌单和用户规则的保留策略。

## 规则与结果协议

规则模型需分开表达筛选、排序、数量限制和刷新策略。新增 `added_at` 的时间范围与排序能力、带种子的随机抽样、结果数量限制；兼容已有用户智能歌单，不能改变旧规则原有含义。

- 所有输入必须校验字段、运算符、类型、范围和数量上限；不接受客户端拼接 SQL 或任意排序表达式。
- 返回客户端可查询的规则能力描述，包括字段、运算符、参数范围、默认值及歌单特有限制，避免 Flutter 和鸿蒙各自猜测。
- 支持规则预览。预览不保存规则、不替换首页当前批次、不改变播放队列。
- 规则保存、恢复默认和生成新批次都要有版本及并发保护。两个客户端同时编辑不能静默后写覆盖；冲突返回可识别错误和最新版本信息。
- 保存成功后以同一事务或可靠的版本切换使规则与结果一致。计算失败时保留旧结果，并明确返回旧结果、过期状态和错误，不展示半生成列表。

结果建议包含：系统键、资料库身份、规则版本、结果版本、生成时间、过期或待刷新状态、匹配总数、实际结果总数、封面预览、分页信息和歌曲摘要。

歌曲摘要复用现有 `TrackSummary` 与媒体解析协议；封面不能只依赖歌曲自身的 `cover_asset_id`，应兼容已有专辑封面回退。确实没有封面时返回明确的缺省状态，不能伪造图片或计数。

分页绑定结果版本或快照。翻页过程中不能重新随机，也不能由于入库变动造成漏项或重复。数量超过 1,000 首时不得无提示截断；列表、详情和播放使用的数量语义应一致。

## 接口建议与兼容性

以下路径均为 `/api/v1` 下的建议新增接口，最终命名可调整，但应在协议文档中给出确定的请求、响应和错误示例。

| 接口建议 | 用途 |
| --- | --- |
| `GET /system-playlists` | 轻量摘要与首页预览，不含整库歌曲 |
| `GET /system-playlists/{key}` | 当前规则摘要及一个分页结果 |
| `GET /system-playlists/rule-schema` | 可编辑字段、参数范围、默认值和限制 |
| `POST /system-playlists/{key}/preview` | 预览规则，不写入持久状态 |
| `PATCH /system-playlists/{key}` | 带预期规则版本保存允许编辑的参数 |
| `POST /system-playlists/{key}/refresh` | 显式换一批，支持请求幂等和批次冲突处理 |
| `POST /system-playlists/{key}/reset-rules` | 恢复默认规则，不删除歌单 |
| `GET` 与 `PATCH /settings/system-playlists` | 读取、修改全局管理开关 |

不提供系统歌单 DELETE 接口，同时保护已有 `/playlists/{playlist_id}` 删除和更新路径。静态 `rule-schema` 路径需避免被 `{key}` 动态路由误匹配。

能力探测建议由 Core 状态接口提供明确标识，例如 `system_smart_playlists_v1`。不支持此能力的旧 Core 应使新客户端隐藏相关管理入口，并明确提示版本不支持；不能悄悄退回客户端固定选曲却宣称是同一功能。

普通 `/playlists`、搜索结果、旧版同步快照与增量歌单实体、计数以及“加入歌单”目标默认排除系统隐藏歌单，保证旧客户端也不会误显示或修改它们。专用接口提供读取与管理，不建议仅加入 `hidden` 字段后要求所有旧客户端自行识别。

规则、批次和全局设置变更应沿用现有事件通道通知客户端，并携带系统键、资料库身份及版本；客户端能够识别漏事件后重读。新模块事件不应强迫客户端重新同步整份歌曲目录。

## 与首页和播放队列的关系

点击首页 banner 先打开该隐藏歌单的详情，不直接改变播放状态。只有点击“播放全部”、某首歌或明确标注的快捷播放按钮才修改播放队列。

- 播放时使用用户正在查看的结果批次和顺序，不得在播放请求内部无提示重新生成另一组歌曲。
- “换一批”、每日刷新、修改规则、关闭管理开关，都不自动替换或中断已经开始播放的队列。
- 队列保存来源信息，例如系统键、显示名称和结果批次，方便播放列表展示“播放来源：今日随听”。不把一次队列编辑写回智能歌单规则。
- 可以继续使用现有播放队列协议，不要求新建另一套播放器。若由 Core 接收结果引用并入队，则须按指定快照解析并原子提交；若客户端提交歌曲 ID，也须完整读取同一快照，不可只入队首屏。
- 结果快照失效时明确提示刷新，不可静默以最新批次替换用户的选择。歌曲不可用时按既有音源策略反馈或跳过并说明原因；不得清空原队列后才发现新结果无法解析。
- Core 离线时允许客户端展示带时间标识的上次结果，并按本机副本能力播放；不能假装已完成规则保存或全局换一批。本阶段不新增离线规则写入队列。

播放页的“最近播放歌曲”与完整播放事件历史仍是单独需求，不应为它们创建这类智能歌单，也不在本次 Core 隐藏智能歌单交付中顺带重构。

## 性能与同步

此功能不能进一步拉长客户端首屏等待。首页只需摘要和少量预览，不能下载六千首后才由客户端生成两个 banner。

- Core 缓存生成结果，合并重复生成任务，避免每个客户端读取都触发全量计算或新的随机结果。
- 目录、规则和时间周期变化应有明确失效策略；提供有效旧结果时标明待刷新状态。不要把每次播放器进度事件都当成失效原因。
- 每日刷新和资料库更新尽量后台计算；首次生成中返回可识别状态，不把空结果误报成“没有符合规则的歌曲”。
- 建议以 6,000 首以上曲库验收：缓存摘要及首屏读取在本机正常负载下 P95 小于 200 毫秒，首次生成与刷新另行测量并记录硬件、库规模和并发数。这是 Core 目标，不等同于已经承诺或测得客户端秒启动。

## 验收清单

1. 全新库、旧库升级、重复启动及并发初始化后，每个系统键只存在一份；普通歌单和用户已有规则不受影响。
2. 今日随听同一批次多端、分页、返回读取一致；跨日与换一批更新；小曲库和零结果正常；不会固定播放标题排序第一首。
3. 新近入库严格按入库时间排序；新增、重扫、元数据编辑、合并和资料源移除场景符合约定；首页预览不限制详情实际数量。
4. 管理开关开关前后均能从首页查看与播放；仅开启时允许管理；关闭不清空数据、恢复默认或中断播放。
5. 界面、旧客户端、直接接口、批量操作及修改标记后再删除等路径，都不能删除或转化系统歌单；尝试失败后数据与事件一致。
6. 规则预览无副作用；非法规则明确拒绝；多端版本冲突不静默覆盖；恢复默认保留稳定歌单身份。
7. 普通列表、搜索、添加目标和旧同步路径不泄露系统歌单；新客户端通过明确能力与专用协议获取它们。
8. 六千首曲库中分页无重复、无遗漏、无静默的 1,000 首截断；封面有回退；计数与当前结果版本一致。
9. banner 打开不播放；点选歌曲从正确位置开始；播放后后台刷新、换一批或改规则不干扰当前队列。
10. 请求重试、并发换一批、Core 重启、切换 Core、资料库重建、客户端离线和陈旧结果引用均有测试。
11. 提供升级测试、规则与生成单元测试、接口保护测试、分页与队列集成测试及性能记录；更新 OpenAPI 与对接示例。

## Core 交付后再继续客户端

Core 完成后应提供最终能力标识、接口样例、默认规则、管理开关路径、错误码、事件与结果版本语义，以及升级后的可测试服务。届时再接入鸿蒙与 Flutter 的首页详情、规则管理和播放来源展示。

本次仅新增此需求文档；不修改 Core 业务代码，不创建真实歌单，不操作在线播放队列，也不继续此前暂停的鸿蒙改动。
